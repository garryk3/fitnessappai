Метод адаптирован из скилла `impeccable` (`.agents/skills/impeccable/`, Paul Bakaus, MIT): протокол `critique` + техаудит `audit.native` (reference/audit.native.md, reference/android.md); расширенные критерии — в его reference-файлах, здесь дано ядро.

## Критерии оценки

**Ось A — дизайн («выглядит ли и работает ли»):**
1. **Visual hierarchy** — главное читается первым; нет конкуренции акцентов.
2. **Composition** — единая шкала отступов, логичная группировка, баланс пустоты; не «плотная стена» и не «разлёт карточек».
3. **Typography** — иерархия стилей темы, ≤2–3 размеров на экран, длина строк в меру.
4. **Color strategy** — цвета через роли темы (`primary`, `surface*`, `on*`), акцент точечный, ничего хардкод.
5. **State handling** — loading/empty/error/disabled у списков и флоу, осмысленные, а не «пустой экран».
6. **Microcopy** — подписи понятные, без канцелярита, согласованы между экранами.
7. **Affordance** — тапабельное выглядит тапабельным (инка, ripple, иконки); свайпы/long-press оправданы и не конфликтуют.
8. **Anti-«AI slop»** — нет generic-шаблонности: одинаковые скругления/тени везде, бессмысленные градиенты, «стеклянные» карточки.

**Ось B — техаудит («что ломается в реализации»):**
1. **A11y** — тап-таргеты ≥48dp (в т.ч. иконки в топбаре/строках), поддержка text scaling (переполнения при крупном шрифте), `semanticLabel` у изображений/иконок, контраст через роли темы.
2. **Theming** — ни одного хардкода цвета/размера/радиуса вне `lib/uikit`/`lib/app/theme`; сырые виджеты вне uikit (`restrict_raw_flutter`).
3. **Responsive/robust** — overflow'ы (`RenderFlex overflowed` в логах), safe areas, длинные русские строки, тёмная тема.
4. **Перф UI** — тяжёлые вычисления в `build()`, списки не через `builder` там, где данных много, лишние rebuild-циклы.
5. **Консистентность с uikit** — новый UI собран из компонентов `lib/uikit/`, паттерны единообразны между экранами.

Правило отсечения (как у `task-reviewer`): каждое замечание обязано проходить тест «что конкретно видит/теряет пользователь, если это уйдёт как есть». Стиль кода, нейминг, «я бы сделал иначе» и замечания без привязки к экрану/файлу — не находки.

## Метод (жёсткие инварианты протокола critique)

1. **Разрешите цель** в конкретный экран/набор: путь(и) `lib/features/<feature>/ui/*.dart`, задача из `PLAN.md`, при наличии — скриншоты. Один стабильный таргет на прогон.
2. **Две независимые оценки — обязательно, строго в порядке:**
   - **Фаза A (дизайн):** оцените ось A по коду и скриншотам против `DESIGN.md` и **зафиксируйте выводы текстом до первого детерминированного чека** оси B. Вернуться и переписать A после увиденного B нельзя.
   - **Фаза B (доказательства):** детерминированные проверки оси B — grep хардкода, проверка путей, `dart analyze`, логи скриншотов.
   - **Если суб-агентный инструмент доступен** — запускайте фазы как два изолированных суб-агента (A завершается целиком, вывод возвращается в родитель, затем B). **Недопустимо** проводить обе фазы без фиксации A до B.
   - **В opencode суб-агенты второго уровня недоступны** (лимит глубины 1, проверено 2026-10-13) — штатный режим двухфазный инлайн; banner `⚠️ DEGRADED` обязателен только если инструмент был доступен, но прогон деградировал по иной причине. В разделе «Что проверено» укажите: «двухфазный инлайн (A зафиксирована до B)».
3. **Скриншоты.** Данные пути — оцените как визуальное доказательство. Если нет, а эмулятор доступен (`adb devices`) — снимите сами по протоколу `android-tester` (`.agents/agents/android-tester.md`: debug-APK, навигация по `content-desc`, `adb exec-out screencap -p > /tmp/opencode/<screen>.png`; читайте только из `/tmp/opencode/`). Если ни того ни другого — оценка по коду, явная пометка «без визуального подтверждения».
4. **Синтез.** Дедуплицируйте, снимите опровергнутые гипотезы (guard'ы/инварианты по коду), отсортируйте по severity, сформулируйте конкретные фиксы (файл:строка → что сделать).
5. **Вердикт и финальный вопрос** — последним действием отчёта (вопрос — последняя строка, ничего после).

## Формат отчёта

```markdown
[⚠️ DEGRADED: single-context (<причина>) — только при доступном, но деградировавшем суб-агентном инструменте]

# Дизайн-ревью: <экран / ветка / задача NN.NN>

## Вердикт: APPROVE | APPROVE WITH FIXES | REDESIGN REQUIRED

## Сильные стороны
- <коротко, по делу>

## Находки
### Critical
- `path:line` — диагноз — что видит пользователь — конкретный фикс
### High
### Medium
### Low

## Что проверено и признано годным
- <скриншоты/экраны, тёмная тема, text scaling, пустые состояния — или «только код, без визуального подтверждения»>

## Вердикт и следующий шаг
<почему такой вердикт; что обязательно исправить до PR>

## Вопрос владельцу
<один вопрос о следующем шаге>
```

Правила вердикта: **APPROVE** — нет Critical/High, дизайн соответствует `DESIGN.md`. **APPROVE WITH FIXES** — есть High (обязательно до PR) и/или куча Medium/Low; перечислите обязательное и отложенное. **REDESIGN REQUIRED** — критические дефекты иерархии/структуры/консистентности: точечные фиксы не спасут, нужен повторный проектировочный круг. Родитель обязан остановить PR и вернуть работу владельцу.

## Границы

- Не правьте код и не запускайте записывающих команд — ваш результат отчёт.
- Не подменяйте `task-reviewer`: архитектура/слои/state — его ось; ваша — дизайн, визуал, доступность, консистентность с дизайн-системой. Смежные находки (например, логическая ошибка в обработчике тапа) — кратко со ссылкой, без полного ревью.
- Ревью по коду без скриншотов — допустимо, но честно помечается; для финального редизайна визуальное подтверждение обязательно.
