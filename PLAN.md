### 67.1 — `dismissActiveReminders` гасит уведомление foreground service тренировки (id 256)

- **Статус:** [x] выполнена (2026-11-19). Реализовано: (1) публичная константа `workoutForegroundServiceNotificationId = 256` в `workout_foreground_service.dart` (договорённость зафиксирована док-комментарием: плагин использует `serviceId` как id уведомления — `ForegroundService.kt`: `startForeground(serviceId, …)`, `notify(serviceId, …)`; подтверждено ревьюером по исходникам 11.0.1); `_serviceId` ссылается на неё. (2) Фильтр этого id в `ReminderService._activeNotificationIds()` (reminder_service.dart) — единственной точке обхода трея: `dismissActiveReminders` больше не гасит и не помечает «доставленным» постоянное уведомление тренировки, `catchUpMissed` не принимает FGS-уведомление за висящее напоминание при коллизии `programDayId == 256`. Тесты: в группе dismiss FGS-добавлено в общий setUp + выделенный тест «не гасится и не помечается», в группе catchUp — тест коллизии id 256 (догон показывает день несмотря на FGS в трее). Гейты: format 0, `dart analyze lib --fatal-infos` 0, `flutter analyze --fatal-infos` 0, full suite 1456/1456; task-reviewer SHIP. Остаточный эдж (принят осознанно, отложен): день с `programDayId == 256`, чьё системное напоминание висит в трее ровно в момент resume, станет «невидимым» для снятия — догон заменит его показом с тем же id (видимого дубля нет, `wasShownOn` гасит повторы).
- **Проблема (аудит 2026-11-19):** `dismissActiveReminders()` (`lib/core/notifications/reminder_service.dart:993-1021`) обходит ВСЕ активные уведомления приложения (`getActiveNotifications`), снимает каждое (`_plugin.cancel(id)`) и для id < `manualReminderIdBase` (1 000 000) пишет в `app_meta` ключ «доставлено» (`reminder_delivered_<id>`). Foreground service тренировки (`flutter_foreground_task` 11.0.1) использует notification id = serviceId = **256** (код плагина `ForegroundService.kt:283,423`). Метод вызывается при каждом `AppLifecycleState.resumed` (`lib/main.dart:83`) и в bootstrap (`lib/app/bootstrap.dart:84-93`). Сценарий бага: тренировка идёт → пользователь свернул/вернул приложение → `_plugin.cancel(id: 256)` гасит персистентное уведомление тренировки (возвращается лишь при следующей смене фазы), а в `app_meta` пишется мусорный ключ `reminder_delivered_256`. Дополнительно — коллизия id: реальный `programDayId == 256` примет FGS-уведомление за висящее напоминание в `catchUpMissed` (`reminder_service.dart:887`) и пропустит догон, а `dismissActiveReminders` пометит «доставку» дня 256.
- **Рабочий план:**
  1. Ввести явную константу id уведомления FGS (256) в одном месте (рядом с `manualReminderIdBase` в `reminder_service.dart` или в `workout_foreground_service.dart` с импортом — выбрать по месту потребления; не дублировать магическое число).
  2. `dismissActiveReminders`: исключить id FGS из снятия и из проставления «доставлено».
  3. `catchUpMissed`: не считать уведомление с id FGS висящим напоминанием дня (filter до проверки).
  4. Проверить остальные обходы `getActiveNotifications` в сервисе на ту же ошибку.
  5. Тесты (`test/core/notifications/reminder_service_test.dart`): активные уведомления {256, dayId, manualId} → снимаются только напоминания, 256 сохраняется, ключ «доставлено» пишется только для dayId; `catchUpMissed` с активным 256 и ненаступившим днём — показ не пропускается; регресс: текущие кейсы догона зелёные.
  6. Гейты: format, `dart analyze lib --fatal-infos`, `flutter analyze --fatal-infos`, full suite; task-reviewer перед коммитом/PR. UI не меняется — design-reviewer не требуется.
- **Проверка:** unit-тесты выше зелёные; на эмуляторе (android-tester, опционально): старт тренировки → свернуть/развернуть → персистентное уведомление тренировки осталось.

### 67.2 — Потеря сегодняшнего напоминания при старте/resume в окне задержки inexact-будильника

- **Статус:** [ ] открыта.
- **Проблема (аудит 2026-11-19):** `rescheduleAll()` (вызовы: `lib/app/bootstrap.dart:84-93`, `lib/main.dart:78-97`) для каждого вхождения делает `cancel(id)` и перепланирует на СЛЕДУЮЩУЮ неделю (`nextInstance`, `reminder_service.dart:1171-1190`). Если приложение открыто в окне между плановым временем напоминания и фактической доставкой inexact-будильника (системная задержка < `catchUpGrace` = 15 мин, `reminder_service.dart:127`), будильник сегодняшнего дня снимается, а `catchUpMissed` (`reminder_service.dart:946-967`) не считает день просроченным (сравнение от планового времени со сдвигом grace) → напоминание за сегодня не приходит вовсе.
- **Рабочий план:**
  1. В `rescheduleAll` не перепланировать вхождение, чьё плановое время — сегодня и находится в пределах grace-окна до/после «сейчас» (будильник ещё может сработать сам); остальные — как раньше (cancel + `nextInstance`).
  2. Альтернатива/дополнение (выбрать при реализации по простоте): после reschedule в bootstrap/main выполнять `catchUpMissed` с учётом снятого сегодняшнего окна — оценить риск двойного показа с опоздавшим системным будильником (claim-before-show в `app_meta` защищает от дублей).
  3. Тесты: reschedule в момент «плановое время − 5 мин» (inexact-задержка) → сегодняшний будильник сохранён; «плановое время + 20 мин» → перепланирован на следующую неделю как раньше; границы grace-окна; регресс: `nextInstance`, exact/inexact-фолбэк, тесты логов доставки зелёные.
  4. Гейты: format, `dart analyze lib --fatal-infos`, `flutter analyze --fatal-infos`, full suite; task-reviewer перед коммитом/PR. UI не меняется — design-reviewer не требуется.
- **Проверка:** unit-тесты границ окна зелёные; на эмуляторе (опционально): напоминание через N минут → свернуть/развернуть приложение до срабатывания → уведомление приходит.

### 69.5 — История: длительность без трёхзначных значений [Medium]
- **Проблема:** плашки статистики показывают время только в минутах — «125 мин», «1 200 мин»; трёх- и четырёхзначные значения читаются хуже, чем «2,1 ч».

### 69.7 — План и История: календарь прижат к верху, без прыжка при смене месяца [Medium]

### 69.8 — План: прошедший день не предлагает запланировать тренировку [High]

### 69.11 — Тренировка: цель подхода учитывает прошлую тренировку [High]
- **Проблема:** бейдж «Цель: 6 повт» в карточке прошлой тренировки берёт параметры позиции — одинаковые для всех подходов. При прошлой тренировке 6/8/9 повторов на 2-м подходе цель показывает то же значение, что и на 1-м, а не результат 2-го подхода прошлой тренировки; прогрессия по подходам не видна.
- **Решение:** передать в `_LastWorkoutCard` текущий номер подхода (`workout.currentSet`) и брать цель из `lastResultsForExercise` — результат с тем же `setIndex` (для латеральных упражнений — соответствующая сторона, иначе максимум/первый по подходу); если результата для этого подхода нет — fallback на параметры позиции (`WorkoutGoalFormatter.perSet`). Расширить `WorkoutGoalFormatter` методом `perSetForCurrentSet(l10n, exercise, results, setIndex)`; бейдж скрывается, если нет ни результата, ни параметров; при смене подхода бейдж обновляется без перезагрузки карточки. В карточке прошлой тренировки подсветить строку текущего подхода (опционально, по design-review).
- **Тест:** unit — 6/8/9 и текущий подход 2 → цель 8, подход 3 → 9; нет результата для подхода → параметры позиции; планка/дистанция; латеральные стороны; widget — переход на 2-й подход меняет бейдж; e2e с прошлой тренировкой, если контракт затронут.
- **Затрагивает:** `lib/features/workout/ui/workout_run_screen.dart` (`_LastWorkoutCard`, `_goalLabel`), `lib/features/workout/domain/workout_goal_formatter.dart`, тесты.

### 69.12 — Тренировка: «Пропустить упражнение» — отдельно от основных действий [Medium]
- **Проблема:** `AppOutlinedButton` «Пропустить упражнение» стоит вплотную под формой подхода (и рядом с «Пропустить отдых» на экране отдыха) — легко нажать по ошибке; действие пропускает всё упражнение и на последнем упражнении завершает тренировку.
- **Решение:** перенести пропуск в менее заметное место — `⋮`-меню в `AppTopBar.actions` (единая точка доступа в подходе и в отдыхе) с подтверждением `AppDialog` («Пропустить упражнение? Несохранённые подходы не запишутся»); из контента кнопку убрать, на экране отдыха остаётся одно основное действие «Пропустить отдых». Сохранить семантику: несделанные подходы не пишутся, на последнем упражнении — завершение с частичными результатами; при необходимости — текстовая `AppTextButton` внизу под разделителем, но не рядом с primary-кнопкой.
- **Тест:** widget — в контенте кнопки нет; пункт меню есть в обеих фазах; диалог отменяет/подтверждает; подтверждение вызывает `skipExercise`; на отдыхе кнопка не соседствует с «Пропустить отдых»; e2e-контракт обновлён.
- **Затрагивает:** `lib/features/workout/ui/workout_run_screen.dart`, `test/features/workout/ui/workout_run_screen_test.dart`, `integration_test/`, `app_ru.arb`.

### 69.13 — Нижнее меню: число вкладок по ширине экрана [Medium]
- **Проблема:** нижний бар жёстко показывает первые 4 пункта (`items.take(4)`), хотя на широких телефонах помещаются все 6; на узких подписи могут тесниться, а пункты «Прогресс»/«История» доступны только через меню.
- **Решение:** в `_buildBottomBar` вычислять вместимость: измерить ширину самой широкой подписи (`TextPainter` с `MediaQuery.textScalerOf` и стилем темы) + паддинги пункта, `count = clamp(floor(availableWidth / itemWidth), 3, items.length)`; показывать первые `count` пунктов в порядке бокового меню (Главная, Упражнения, Программы, План, Прогресс, История) — «Профиль» и «Настройки» не выводятся (их нет в `_menuItems`); пункты равной ширины (`Row` + `Expanded`/`NavigationBar`), текст в одну строку (`maxLines: 1`, `softWrap: false`), без переноса и обрезки. Пересчёт при изменении ширины и масштаба шрифта; если активная ветка вне показанных — не подсвечивать ни один пункт (как сейчас `isMenuOnly`); на широких экранах — все 6.
- **Тест:** widget — 360dp: N вкладок равной ширины, подписи не переносятся; 600dp: все 6; активная «История» не подсвечивает чужую вкладку, переходы работают; `textScaler` 1.3 уменьшает число вкладок без overflow; регресс существующих тестов навигации.
- **Затрагивает:** `lib/app/responsive/adaptive_navigation.dart`, `test/app/responsive/adaptive_navigation_test.dart`, `DESIGN.md` §11, при необходимости `app_breakpoints.dart`.
