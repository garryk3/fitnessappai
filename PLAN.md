### 57.1 — «Сохранить» в форме упражнения без выбранных мышц — тихий no-op
- **Статус:** открыта.
- **Проблема (QA, TEST_PLAN TC-007, 2026-10-25):** в форме упражнения при заполненном имени валидация имени работает («Введите название»), но тап «Сохранить» БЕЗ выбранных групп мышц — тихий no-op: нет валидационного сообщения/снекбара, форма молча остаётся открытой, пользователь не понимает, что мешает сохранить. Подтверждено ретестом в прогоне релиза (историческая заметка «не срабатывает» подтверждена как дефект UX).
- **Предполагаемая причина:** сабмит формы упражнения (`lib/features/exercises/` — форма/контроллер) требует непустой список мышц (тихий ранний return при пустом списке), но пользователь об этом никак не информируется — ошибки/подсказки при пустых мышцах нет.
- **Решение/Тест:** при пустом списке мышц тап «Сохранить» должен давать явное валидационное сообщение/снекбар (или пометку у блока мышц); ретест — `TEST_PLAN.md` TC-007 (проверка валидационного сообщения при пустых мышцах).

### 57.2 — Поведение resumed-тренировки после импорта БД (нужно решение владельца)
> **Решение владельца (2026-10-25):** импорт БД обязан чистить локальные чекпойнты (в момент импорта не может быть начатой тренировки); чекпойнт вводится TTL — не восстанавливать тренировки старше 12 часов от `startedAt`.

- **Статус:** ✅ 2026-10-25, PR #269 (d809b97). task-reviewer: SHIP (после добавления регресс-теста сброса `restoredCheckpoint` дефолтным клирером в `sync_controller_test`). 1349/1349. **Реализовано:** Фикс A — `SyncController.importDatabase()` после успешного импорта вызывает `_checkpointClearer()` (новый typedef `CheckpointClearer`, дефолт: `WorkoutCheckpoint.clear()` + `restoredCheckpoint = null`) до `_setStatus(importDone)`, т.е. до `restartApp()`; Фикс B — `bootstrap()` через `_restoreCheckpoint(sl)`: TTL (`WorkoutCheckpoint.ttl = Duration(hours: 12)`, `startedAt` строго старше — удаление) и факт (`ProgramRepository.getDay(programDayId)` != null); невалидный снимок удаляется, redirect не происходит. Тесты: bootstrap ×3 (свежий валидный / граница TTL ровно ttt → удалён / день 999999 → удалён), sync_controller ×1 дефолтный клирер через fake path_provider (зеркало lib-стороны фикса A), settings_screen ×1 ассерт clear. Гейты зелёные.
- **Проблема (QA, TEST_PLAN TC-175, 2026-10-25):** после импорта БД (диалог «Импорт выполнен» → «OK» → перезапуск приложения) приложение открылось на экране активной (resumed) тренировки — восстановление checkpoint из опрокинутого состояния. Неясно, ожидаемое ли это поведение (checkpoint переживает импорт/перезапуск) или неожиданное: при импорте чужой/целиком замещающей БД восстановленная тренировка может ссылаться на несуществующие в новых данных сущности.
- **Причина (диагностика по коду, 2026-10-25):** три звена: (1) `workout_checkpoint.json` пишется на диск по таймеру 5с/подходам/фону и удаляется только при `dispose()` с фазой `finished`/`idle` (`workout_run_screen.dart:160-177`) — force-stop незавершённой тренировки оставляет файл; (2) `restoredCheckpoint` — глобал, читается один раз в `bootstrap()` (`bootstrap.dart:93`); (3) `restartApp()` (импорт: `settings_screen.dart:428`) пересоздаёт роутер через `AppRouter.create()`, который переиспользует **stale in-memory `restoredCheckpoint`** и redirect'ит на `/workout/run` (`router.dart:63-70`) — локальный чекпойнт не согласован с заменённой БД (ID дня может не существовать).

  1. **Фикс A (безусловная чистка при импорте):** в `SyncController.importDatabase()` после успешного `_syncService.import()` — `await WorkoutCheckpoint.clear()` и `restoredCheckpoint = null` **до** `restartApp()`; пере-созданный роутер не получает stale-value.

### 57.3 — Восстановленная тренировка не переписывает чекпойнт заново: повторный force-stop теряет её навсегда
- **Статус:** ✅ 2026-10-28, PR #270 (c1954a3). task-reviewer: SHIP. 1350/1350, e2e 19/19.
- **Проблема (QA, TEST_PLAN TC-202, 2026-10-25):** ретест 57.2 (PR #269 стабильно PASS по всем кейсам: TC-199–TC-201) обнаружил соседний дефект: тренировка, восстановленная из чекпойнта (экран открылся по redirect'у), потребляет файл чекпойнта на диске (`_initLoad`: load → clear) и далее НЕ переписывает его: таймер 5с (`_saveCheckpoint()`) не срабатывает, повторный force-stop/краш на восстановленной тренировке теряет её навсегда (перезапуск открывает /home, файла нет, предупреждений нет). Воспроизводится стабильно (3 попытки), цепочка «restore → второй kill».
- **Предполагаемая причина:** `WorkoutController.restoreFromCheckpoint()` (`lib/features/workout/domain/workout_controller.dart:203`) не задаёт `_context` (`WorkoutSessionContext` присваивается только в `start()`), а `_saveCheckpointIfNeeded()` (`lib/features/workout/ui/workout_run_screen.dart:242-251`) возвращает раньше при `ctx == null` — восстановленная сессия не проходит гвард сохранения ни в таймере 5с, ни в `dispose()`. Код старый (consume-restore и `_context`: был и до PR #269), не введён фиксом 57.2; ранее маскировался: до первого восстановления файл пишет дисковый таймер живой сессии.
- **Решение/Тест:** при `restoreFromCheckpoint` восстанавливать/заполнять `WorkoutSessionContext` (programId/programName/dayIndex/programDayId известны из чекпойнта и экрана) — тогда таймер 5с и dispose продолжают переписывать чекпойнт в течение всей восстановленной сессии; ретест цепочки «restore → force-stop → restore → force-stop»: после каждого kill чекпойнт жив (TC-202), финальное завершение сохраняет сессию без дублей.
- **Реализовано (2026-10-28):** `WorkoutController.restoreFromCheckpoint` принял именованный параметр `context: WorkoutSessionContext?` и присваивает `_context` (раньше его ставил только `start()`); `workout_run_controller` строит контекст один раз до ветвления restore/start в обоих загрузчиках (`_loadSingleExercise` и `_loadFromProgram`) — восстановленная сессия получает полный контекст живых данных (programId/programName/programDayId/dayIndex/variant/exerciseRestSeconds), guard `_saveCheckpointIfNeeded` больше не блокирует запись: таймер 5с, подходы, pause/dispose переписывают `workout_checkpoint.json` после потребления снимка. Тесты: `workout_controller_test` — в round-trip добавлен контекст и ассерт `restored.context same(context)`; `workout_run_screen_test` — новый регресс TC-202 «восстановленная → lifecycle pause → чекпойнт переписан (saveCalls=1)». Ретест в эмуляторе (TC-202, 2026-10-28): PASS — mtime снимка двигался, «restore → force-stop → restore → двойной force-stop» без потери, финальное завершение ровно одна сессия.

### 57.7 — «Сделать активной» с несколькими активными программами — снимена как «не дефект»
- **Статус:** ✅ 2026-10-28 — закрыта решением владельца **без кода**: несколько активных программ одновременно — бизнес-требование, не дефект. Находка TC-204 интерпретирована тестировщиком по устаревшему инварианту «ровно одна активная» (TC-113 — заготовка 54.4, раньше единственность была валидна). Ожидания TEST_PLAN исправлены (TC-204 факт + инвариант): бейдж «Активная» имеет каждая активная программа, счётчик на Главе «Активная программа (N)» — штатный вид при N>1. Фиксировать «снятие флага» в будущих прогонах НЕ нужно; при прогонах проверять наоборот согласованность БД↔UI при нескольких активных (каждая is_active=1 имеет бейдж).
- **Проблема (QA, TEST_PLAN TC-204, FAIL; найдено в TC-197/шаг 3, 2026-10-28):** «⋮» → «Сделать активной» на неактивной программе ставит ей бейдж «Активная», но НЕ снимает флаг с прежних: в БД `programs.is_active=1` у нескольких программ (в прогоне после серии действий все 4 программы активные; инвариант «ровно одна активная» TC-113 нарушен). На Главе виден счётчик «Активная программа (2)» — семантика выбора активной при N>1 не определена (быстрый старт, планирование недели).
- **Предполагаемая причина:** `_makeActive` (programs_screen.dart) → репозиторий/DAO: `update programs set is_active=1 where id=?` без сопутствующего `set is_active=0 where id<>?` (нет транзакции «снять у всех → поставить у одной»); «Деактивировать» — отдельная корректная операция.
- **Решение/Тест:** атомарная операция «сделать активной» (снять у остальных + поставить у выбранной в одной транзакции); widget-тест «после set-active ровно одна активная» на уровне DAO/контроллера; ретест TC-197 (шаг 3) + TC-204 (БД-проверка) + поведение Главы/плана недели при N=1.
